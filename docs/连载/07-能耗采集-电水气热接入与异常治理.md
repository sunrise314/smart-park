# 能耗采集：电水气热接入与异常治理

从这一章起连讲两章能耗。能耗是园区运营里"降本增效"故事的主角：电费水费是园区仅次于人力的第二大成本项，抄表不准、分摊不清、异常发现不了，都是真金白银的损失。这一章先讲数据的源头——采集。采集是整个能耗体系的地基，地基歪了，后面所有看板和分析都是空中楼阁。

## energy_collect：一张表装下四类能源

采集数据的落点在 `energy_collect` 表，`EnergyCollectDO` 的完整原文我在第 2 章贴过一部分，这里把核心字段按设计意图重新组织一遍：

```java
@TableName("energy_collect")
public class EnergyCollectDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * 设备名称
     */
    private String deviceName;
    /**
     * 设备类型：电表/水表/气表
     */
    private String deviceType;
    /**
     * 能耗类型：电/水/气/热
     */
    private String energyType;
    /**
     * 采集时间
     */
    private LocalDateTime collectTime;
    /**
     * 采集状态：采集正常/采集异常
     */
    private String collectStatus;
    /**
     * 能耗数值
     */
    private BigDecimal energyValue;
    /**
     * 采集频率，单位分钟
     */
    private Integer collectFreq;
    /**
     * 异常次数
     */
    private Integer exceptionCount;
    /**
     * 操作人账号
     */
    private String handleUser;
}
```

这张表有两个容易混淆的字段对，先掰扯清楚。

**`deviceType` 和 `energyType` 为什么要分开？** 设备类型回答"数据从哪台设备来"，能耗类型回答"数据计量的是什么东西"。大多数情况下两者一一对应——电表出电耗、水表出水耗——但边界场景正是设计价值所在：热量表计的是"热"，但很多园区的热计量走的是"载热流体"的思路，一块设备同时出流量和温差两个量；换热站的采集设备出的数据既关联热也关联水。分成两个字段后，设备维度的运维统计（电表在线率）和能源维度的成本统计（全园电费）各自独立，互不干扰。

**`collectFreq` 采集频率为什么存在数据行里？** 频率看起来是"设备配置"而不是"数据事实"。原项目把它放在采集记录里有它的道理：采集频率可能随时间调整——白天高峰 15 分钟一采，夜间低谷 60 分钟一采——落在每条记录上，这条数据"以什么节奏产生"就固化了。后续做能耗强度分析（每小时的耗电量）时，必须知道每条数据代表的时间跨度才能折算功率，频率字段就是折算的依据。

**`energyValue` 用 BigDecimal**，和上一章停车金额同理，表计读数是十进制小数，浮点误差在累计量上会被放大。顺便说，这个字段存的是**表底数（累计读数）还是区间用量**，原项目没有显式约束——这是我二开时明确的第一个口径：存表底数。理由是表底数是设备的直接事实，区间用量是派生值（本次读数减上次读数），派生值出错可以重算，事实丢了就丢了。这和第 5 章"实付金额不落库"是同一条纪律的两面：**事实落库，派生计算**。

## 采集链路：定时调度到落库的完整路径

原项目的采集实现放在 energymgmt 子模块的 datacollect 包里（12 个文件，含采集任务与配置管理），整条链路是：infra 模块的定时任务按 `collectFreq` 触发 → 采集服务按设备清单轮询表计 → 拿到读数写 `energy_collect` → 异常时更新采集状态与异常计数。

单园区场景下，这套轮询完全够用。但有几个工程细节是原实现留白、我在二开时补上的，逐个说。

**第一是采集失败的记账，不只是记状态。** `collectStatus` 标记单次采集成败，`exceptionCount` 累计异常次数——这两个字段配合，能回答"这台设备最近正常吗"和"这台设备今年以来坏了多少次"。但只记状态不记现场，运维还是两眼一抹黑。我加了一张轻量的采集日志表，失败时记录异常类型（超时/校验错/连接拒绝）和原始报文摘要。表计异常九成是通信问题，日志里一条"TCP 连接拒绝"能直接把排查指向网络而不是设备。

**第二是断点补数。** 采集服务重启、网络中断，都可能造成一段时间的数据空洞。空洞对能耗分析的杀伤力比对停车账单大得多——账单少一张用户会投诉，能耗曲线少一段，日耗量就直接算错。我的做法是每次采集成功后对比上次成功读数的时间戳，跨度超过两个采集周期就标记空洞区间，由修复任务按设备支持的历史读数接口回捞。设备不支持回捞的（老式脉冲表），空洞区间按相邻周期插值并在数据上打"估算"标记，绝不假装它是实测值。

**第三是写入批量化。** 园区几百块表、15 分钟一采，单次采集任务就是几百行插入，直接单条 insert 的开销可以接受但不优雅。我把同一次调度周期内的读数攒成批量插入，任务耗时下降明显。批量的边界要留意事务大小——一次调度周期一个事务，失败整批重试，避免半批落库造成"半点数据"。

## 异常数据的第二层：读数合理性校验

`collectStatus` 管的是"采集动作"的成败，但采集成功不代表数据可信。表计读数还有一类问题：**读数本身不合理**。比如电表读数突然从 5000 跳到 99999（表计故障或换表）、水表读数倒退（表计维修后清零）。这类问题采集是"成功"的，状态字段完全看不见。

我在二开时加了一道合理性校验：新读数与上一次读数比较，增量超过该设备历史峰值增量的若干倍（或读数倒退）就标记待人工确认，同时触发告警。读数倒退的处理有一个专门的业务分支：换表。换表是合法的倒退，但换表后新表的底数和旧表的累计量要拼接——旧表止数加新表起数才是连续的账。园区换表不告知系统，月底的能耗账就出现负数，这个坑我真实踩过，所以校验里专门把"倒退 + 存在换表工单"识别为合法路径。

## 采集任务的组织：调度、并发与顺序

补数和校验讲的是"坏了怎么办"，这一节讲"正常的采集任务怎么组织"。几百块表、多协议、15 分钟周期，任务组织得好不好直接决定采集服务的稳定性。

**调度粒度按设备组而不是按设备。** 原项目按 collectFreq 把设备分频次调度，我的改造是把设备按"频次加协议"分组：15 分钟一采的 Modbus 电表是一个组，60 分钟一采的 NB-IoT 水表是另一个组。每个组一个调度槽，组内并发受连接池约束。分组的收益在故障隔离：某个协议的连接器卡死，只拖住自己那一组，其他组照常采集——全局单队列的调度，一个慢协议能拖垮整个采集周期。

**并发上限以设备侧承受力为准。** 采集器（集中器）的并发处理能力通常远低于服务端，一味的客户端并发只会把采集器打挂。我给每个协议组配置了并发上限与请求间隔，宁可用稍长的采集窗口换取设备侧的稳定。采集窗口的控制也要现实：15 分钟周期并不要求 15 分钟内采完，只要在下一个周期开始前完成就行——把"周期"理解为截止时间而不是执行时长，调度设计会从容很多。

**读数落库的顺序保证。** 同一设备的读数必须按采集时间顺序落库，乱序会造成"上次读数"比较逻辑（合理性校验的基准）用错参照。落库侧我按设备号做简单分区串行（同一设备的读数进同一队列），不做复杂的全局排序——时序场景里，单设备有序就够了，全局有序是伪需求。

这些组织细节没有一样是高深的，但它们共同决定了采集服务是"安静地稳定"还是"间歇地抽风"。物联网采集这类长跑型任务，工程组织的权重高于算法技巧。

## 协议适配层：四种表计，一条链路

采集链路的第一公里是协议，这一节的实战密度很高。园区的四类表计，接入方式往往各不相同：

**电表**是最规整的，主流走 DL/T 645 或 Modbus-RTU，通过采集器（集中器）汇聚后转 TCP 上平台，读数请求-应答式，主动轮询即可。**水表**分两种：智能水表带远传模块走 NB-IoT 直连运营商平台，平台侧对接运营商的开放接口拉数据；老式水表靠光电直读采集器，方式与电表类似。**气表**因为防爆要求，通常由燃气公司的系统管理，园区平台拿到的往往是对方系统的推送或周期文件。**热量表**多走 M-Bus 总线，由换热站的网关统一转出。

这四种来源拉通之后，我沉淀下来的适配层结构是：协议连接器（连接管理、读写原语）→ 报文解析器（字节流到结构化读数）→ 统一读数模型（设备 ID、读数值、读数时间、质量标记）。三种角色各司其职，新增一种表计就是新增一对连接器与解析器，下游全链路无感。原项目的 datacollect 包把适配代码混在采集任务里，我抽出来单独成层——这也是模块 framework 目录存在的意义：**适配逻辑与业务逻辑的分界墙**。

对接外部系统（燃气公司平台、运营商 IoT 平台）要多想一层：对方的接口限流、数据延迟、字段口径都不受你控制。我的经验是对外部来源一律做"接收即落原始报文"的留存，解析失败不丢证据，接口变更时重放原始报文就能定位是哪一方动了格式。

## 电价与折算：从 kWh 到钱，再到标煤

采集到的读数是物理量（千瓦时、立方米），业务要用的是经济量和管理量，中间隔着两把换算尺子。

第一把是**电价时段**。工商业电价分峰平谷（尖峰）时段，不同时段单价差可达三倍。能耗监测如果只看电量不看时段，会发现"这个月电量没涨电费涨了三成"——那是时段结构变了（生产排班挪到了峰段）。我把电价时段表做成配置（时段区间加单价），采集明细按时段打标后，区域监测的每一个电量数字都有对应的电费口径，领导看板上的"本区电费"才经得起追问。

第二把是**折标煤系数**。园区要向上级单位报送综合能耗，口径通常是吨标煤（标准煤当量），电、水、气、热各有国家规定的折算系数。折算本身是乘法，难的是**系数管理与口径一致**——系数更新时历史数据要不要重算？我的原则与停车章的方案版本一致：折算系数带版本与生效期，报表按报送期当时的系数折算，重算与否做成显式选项。能源报送是合规动作，口径的稳定性比数字的最优更重要。

这两把尺子装好之后，同一份采集数据能同时输出三种视图：物理视图（kWh/m³）、经济视图（元）、管理视图（tce 标煤）。视图是算出来的，不是各存一份——又是"事实与派生分离"的熟悉旋律。

## 数据质量分：给每条读数一个可信度

上一章讲了采集异常的治理（状态、计数、补数、换表），这一章把它升级成一个体系化的指标：**数据质量分**。这个设计来自我的一个教训——某月园区向总部报送能耗数据，报表组发现两个园区的"单位面积能耗"差了近一倍，排查了两周才发现是乙园区三分之一的电表数据缺失，汇总口径把缺失当成了零耗。数据缺失不可怕，可怕的是缺失被静默地当成了正常值。

质量分的做法是给每个设备每月算一个 0 到 100 的分数，扣分项全是硬指标：采集成功率（异常次数占比）、数据完整率（应采条数与实采条数之比）、读数合理性（触发过待确认标记的次数）。分数低于阈值（比如 80）的设备列入治理清单，责任人按清单修设备、补数据。月报里每个汇总数字旁边标注数据质量——"本区单位面积能耗 42 度/平方米（数据质量 93 分）"，阅读者自己掂量可信度。

质量分体系的代码量不大（一个定时聚合任务加一张分数表），但它改变的是组织行为：设备运维从"坏了才修"变成"按分数治理"，能耗数据的用户（财务、招商、领导）第一次有了判断数据可信度的依据。这是我认为二开过程中性价比最高的一个自创设计。

## 从采集到监测：数据准备好了吗

这一章结束时，`energy_collect` 表里已经有了一套可信的时序数据：设备维度齐全、状态与异常可追溯、空洞有标记、换表有衔接、每条数据带质量标记与时段标、钱和标煤的换算尺子就位。这是下一章的全部原料。

下一章讲能耗监测：AreaMonitor 的区域监测模型、分摊分析的口径设计、以及园区领导最关心的那张能耗看板怎么搭。数据采集解决了"有没有"的问题，监测分析要解决"对不对、省不省"的问题——那是能耗业务真正出价值的地方。
