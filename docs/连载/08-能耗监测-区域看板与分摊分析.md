# 能耗监测：区域看板与分摊分析

上一章把采集的地基打好了：`energy_collect` 里躺着一套可信的时序数据。这一章往上盖楼——区域监测模型、单位面积能耗的分摊口径、同比环比的趋势分析，最后合成园区领导每天要看的那张能耗看板。监测层的关键不是画图，是**把物理读数翻译成管理语言**。

## area_monitor：分区能耗的聚合快照

区域监测落在 `area_monitor` 表，`AreaMonitorDO` 原文：

```java
@TableName("area_monitor")
public class AreaMonitorDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * 区域名称
     */
    private String areaName;
    /**
     * 区域面积，单位㎡
     */
    private Integer areaSize;
    /**
     * 能耗总量
     */
    private BigDecimal totalEnergy;
    /**
     * 单位面积能耗
     */
    private BigDecimal unitEnergy;
    /**
     * 能耗状态：正常能耗/能耗异常
     */
    private String energyStatus;
    /**
     * 关联设备数
     */
    private Integer deviceCount;
    /**
     * 同比变化
     */
    private BigDecimal yoyChange;
    /**
     * 环比变化
     */
    private BigDecimal momChange;
    /**
     * 操作人账号
     */
    private String handleUser;
}
```

这张表的本质是**聚合快照**：区域是聚合的维度，总量、单位面积能耗、同比环比是聚合的结果。它和上一章 `energy_collect` 的关系，是"事实明细"与"聚合视图"的关系——明细回答"哪块表几点读数多少"，快照回答"A 区这个月能耗怎么样"。

表里有三个字段是这一章的主角。

**第一个是 `areaSize` 区域面积**。看起来平平无奇，但它是整个分摊体系里最关键的分母。有了它，才有 `unitEnergy` 单位面积能耗——这个指标让不同大小的区域变得可比：A 区 8000 平方米这个月用了两万度电，多不多？不知道。A 区单位面积能耗 2.5 度/平方米，隔壁 B 区 1.8 度/平方米——这就马上引出"为什么 A 区比 B 区高出近四成"的问题，管理动作就是从这个差异开始的。园区能耗管理的第一性指标就是单位面积能耗，没有之一。

**第二个是 `yoyChange` 同比与 `momChange` 环比**。同比是和去年同期比（剔除季节因素：夏天开空调、冬天供暖，环比会"虚高"），环比是和上个月比（看短期趋势）。两个指标并存的原因就在这：单看环比，七月比六月能耗涨三成会吓死人，但同比一看去年七月也涨这么多，纯属季节规律；单看同比，今年二月比去年二月涨了，但可能只是二月多了一天，环比一对照才见异常。能耗异常的判定，永远要两个指标交叉着看。

**第三个是 `energyStatus` 能耗异常状态**。这个字段是监测层的"报警器"，正常能耗/能耗异常两态。怎么算异常？原项目没有把规则写死在代码里，我的二开定了一条可配置的规则：单位面积能耗的同比涨幅超过设定阈值（比如 30%）且排除节假日与季节因素，标记异常并推送。阈值可配置很重要——研发办公区和生产车间的能耗基线完全不同，一张全局阈值要么误报一片要么形同虚设，按区域类型配阈值才实际可用。

## 分摊口径：公摊电费怎么算才没人有意见

园区能耗里最吵的架，从来不是"用了多少"，而是"谁该摊多少"。分摊的口径问题，原项目的表结构没有直接给出答案（area_monitor 是区域维度，不是租户维度），我在二开时基于这套模型补了分摊逻辑，这里把口径讲清楚。

园区电力结构通常是：总表下面挂分表，分表对应租户，中间还有公区负荷（大堂空调、电梯、景观照明、地下车库照明）。租户分表读数之和永远小于总表读数，差值就是线损加公摊。分摊公式我采用"按面积为主、按用量为辅"的两段式：

- 各租户分表实计部分，按分表读数直接结算——这是自己用的，没争议；
- 公区与线损的差值，按各租户的承租面积占比分摊——公区服务所有人，面积是公认的分摊基准。

这套口径的落库方案：分摊不落 `area_monitor`，而是生成独立的分摊账单（结构上和上一章停车的账单同形：金额、状态机、减免、缴费）。这样第 6 章讲的整套账单闭环——BigDecimal 计算、优惠减免、催缴补缴——直接复用到水电分摊上，一条业务链路两处使用。这也侧面解释了为什么停车那两章我讲得那么细：**账单模型是园区平台的公共底座**。

## 看板：从表到图的最后一公里

energymonitor 包（10 个文件）提供监测端的接口层。看板的数据组织我总结成三个视图，每个视图对应一类管理问题：

**总览视图**回答"园区整体怎么样"：今日/本月能耗总量、总览的单位面积能耗、能耗异常区域数。数据来自 area_monitor 的全园聚合，配上采集侧的设备在线率——能耗看板永远要带设备健康度，不然"能耗骤降"你分不清是省电了还是电表掉线了。这是采集章和监测章在展示层的交接点。

**区域视图**回答"哪里在耗电"：按区域列单位面积能耗排行、同比环比色阶。这张图是管理动作的触发器——排行尾部（能耗强度最高）的区域自动成为重点排查对象。

**趋势视图**回答"变化的方向"：全园及各区域的 24 小时负荷曲线、近 30 天趋势、同比曲线。24 小时曲线有个实战妙用：凌晨两点的基线负荷（基础负荷）如果持续走高，大概率是空调水系统没人管、设备空转，这类"看不见的浪费"只有负荷曲线能暴露。

看板接口的性能设计与第 6 章态势统计同构：聚合下推 SQL、结果短 TTL 缓存、写操作（新的采集数据落库）后主动失效。时序数据量大之后还有一个动作——预聚合：按天粒度的区域能耗汇成一张日汇总表，看板查日汇总而不是扫明细，明细表只服务钻取。采集表跑半年就是几十万行，预聚合是把看板响应钉在毫秒级的必要投资。

## 分摊的工程落地：从口径到账单

上一章末尾说过分摊口径，这一节把它落到表和任务上，因为"口径讲清楚了"和"系统能自动算"之间还隔着一段工程路。

分摊的输入是三个：当月总表读数、各租户分表读数、各租户承租面积。计算任务按月跑，步骤是固定的四步：先按读数算出各租户实计量；再用总表读数减全部实计量得公摊量（含线损）；然后按面积占比把公摊量摊到各租户；最后把"实计加分摊"折成费用生成分摊账单。整个流程我用一个事务方法实现，跑完输出一份分摊明细报表供财务复核——**先复核后出账**，分摊账单在财务确认前停在"待确认"状态，确认后才进入正常的缴费流程。

有两个工程细节要交代。**一是公摊率的监控**：公摊量占总量的比例（公摊率）是个健康指标，正常园区在 5% 到 15% 之间，突然飙升说明有计量异常（分表坏了、有偷接、有新装负荷没挂分表）。分摊任务每次跑完都输出公摊率，超阈值即告警——它经常是设备问题的第一个信号。**二是面积数据的来源**：承租面积必须是企业档案里的权威数据，分摊任务不允许手工录入面积，杜绝"数据打架"。这也呼应了本章的主线：分摊是主数据消费方，档案数据的质量直接决定分摊的公信力。

分摊结果落库成账单后，走的就是第 6 章讲的完整闭环：优惠减免、催缴、对账全部复用。一个租户的水电分摊账单和停车月卡账单在同一个账单中心呈现、同一条支付链路缴清——对财务是一个入口，对租户是一张合并的账。这份"合并体验"是园区运营方给我的需求清单里排位最高的项，而它的实现成本几乎为零，纯粹是模型设计正确带来的红利。

## 日汇总表：预聚合的落库形态

上一节末尾提到预聚合，这里给出具体的落库形态。我的日汇总表按"区域加日期加能源类型"粒度建行，核心列：区域 ID、日期、能源类型、总量、峰平谷分项量、折算电费、折算标煤、数据质量分、参与汇总的设备数与缺失设备数。生成方式是每日凌晨的聚合任务扫前一天的采集明细——注意汇总任务本身幂等：重跑一次，当天行被覆盖而不是翻倍。

这张表上线后看板的查询形态彻底变了：全园月度趋势是 31 行的 SUM，区域对比是按区域 GROUP BY，全部命中窄表索引，毫秒级返回。它同时是第 9 章会讲的"同比环比"的数据源——同比就是拿当前行和 365 天前的同区域同能源类型行做除法，索引之下也是毫秒级。

汇总表还有一个隐性价值：**它是数据修复的收口层**。采集侧补了数、换表拼了账之后，只要重跑对应日期的汇总任务，所有下游视图自动修正——修复动作有明确的收口点，不需要在各视图逐一订正。

## 能耗强度基准：让"高"和"低"有参照

区域看板把单位面积能耗排了序，但排序只能比出相对高低，回答不了"这个数值本身正不正常"。研发楼 60 度/平方米每年正常吗？没有参照物的话，谁也说不了话。

参照物来自两个渠道。**内部基准**是园区自己的历史数据：每个区域类型取过去十二个月的单位面积能耗中位数作为基准线，当前值与基准的偏离度就是"异常程度"——这个渠道完全自主，随数据积累自动进化。**外部基准**是行业对标值：办公类建筑、轻工类厂房的能耗限额有公开的行业数据可以引入。外部基准用于给园区定位（我们在同类园区里算好还是差），内部基准用于日常管理（哪个区域在恶化）。

两者落库的形态是一张基准表（区域类型、基准值、基准来源、生效期），区域监测的异常判定从"拍脑袋阈值"升级成"基准偏离度"——面积、业态不同的区域终于可以在同一把尺子下对话。这一步做完，area_monitor 里的 energyStatus 才真正立得住：异常不再是"比上月涨了 30%"这种容易被季节因素愚弄的信号，而是"偏离同类区域基准 40% 以上"的实质判定。

## 从数字到行动：能耗管理的激励闭环

监测层做到最后，我补上了业务闭环的最后一环：**让数字驱动行动**。三个动作。

**月度能耗排名**：按单位面积能耗给区域（进而到企业租户）排名，红黑榜公示。排名本身不罚钱，但公示的压力是真实的——没有哪个企业愿意连续三个月挂在红榜第一名。

**异常工单化**：energyStatus 判定为异常的区域自动生成核查工单，指派给物业工程口，核查结论（设备故障、工艺变化、计量异常、真实浪费）回填归档。异常从"看板上的颜色"变成"待办里的事件"，处置率第一次可以被考核。

**节能建议输出**：基于负荷曲线与时段结构给出针对性建议——基础负荷偏高的区域查夜间空转、峰段占比偏高的企业建议错峰生产。这些建议由规则模板生成（每种异常模式一条建议模板），不追求智能，追求稳定可解释。

这三个动作的代码量加起来不到监测层的一成，但园区能耗管理的"故事"到此才完整：采集保证数据真实，监测发现哪里异常，行动让异常收敛。技术平台的价值最终要落到组织行为的变化上——这句话写给所有做企业系统的同行。

收官前再留一个小技巧：**看板的数字都要能"点下去"**。领导看着看板问"这个区域为什么高"的时候，最好的体验不是他去找报表系统，而是直接点那个数字，下钻到构成它的设备明细、再到具体的采集记录。下钻路径的实现依赖一个朴素的前提：从看板指标到日汇总到采集明细，每一层的维度键（区域、能源类型、日期）保持一致贯通。这也是为什么我在设计日汇总表时坚持带齐维度键——看板的每一层下钻，都是一次带着维度条件的查询，维度断了，下钻就断了。数字可下钻的看板，才是一份"自解释"的看板。

## 监测层的边界

最后说说这张 area_monitor 表"不做什么"。它不做实时告警（那是设备与安防域的事，下一章讲）、不做计费结算（那是账单域的事）、也不存储明细（明细永远在采集表）。它只做一件事：把能耗数据翻译成区域维度的管理快照。

把职责边界收窄的好处马上体现在维护上：分摊口径要改，只动分摊逻辑；阈值规则要调，只动异常判定；监测模型扩展一个维度（比如按企业聚合），只是多一张同构的快照表。窄表加窄逻辑，改起来不牵一发动全身。

能耗两章到此收官。下一章转向综合安防——视频监控怎么接入、实时告警怎么流转。那是园区平台里对实时性要求最苛刻的一条线，也是本章埋的"设备在线率"问题的完整答案。
