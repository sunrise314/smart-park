# 停车上：车位台账与账单生成

从这一章开始讲停车。停车是园区业务里离钱最近的一条线：临停收费、月卡车位租金、欠费催缴，每一分钱都要有账可对。这条线我拆成两章——本章讲车位台账与账单生成，下一章讲计费计算、优惠减免与催缴闭环。先说车位，因为账单是从车位的使用事实里长出来的。

## 车位台账：一车位一行的物理世界映射

原项目的车位模型很朴素，`ParkingSpaceDO` 对应 `parking_space` 表，原文：

```java
@TableName("parking_space")
public class ParkingSpaceDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * [车位编号]
     */
    private String spaceCode;
    /**
     * [停车场名称]
     */
    private String parkName;
    /**
     * [车位类型] 如:固定/临时
     */
    private String spaceType;
    /**
     * [车位状态] 如:空闲/占用/预约中
     */
    private String spaceStatus;
    /**
     * [租用信息]
     */
    private String rentInfo;
    /**
     * [预约用户]
     */
    private String orderUser;
    /**
     * [使用时长] 单位分钟
     */
    private Integer useDuration;
    /**
     * [操作人账号]
     */
    private String handleUser;
    /**
     * [备用字段1] 禁行原因 / 停用原因
     */
    private String reserve1;
}
```

这个模型把车位的三种现实形态都装进来了。**类型**上分固定与临时：固定车位对应长租（包月包年，租用信息里挂着租约），临时车位对应即停即走（按使用时长计费）。**状态**上是空闲、占用、预约中的三态机：预约中是给"访客预约车位"这类场景留的中间态——访客预约进园时可以顺带锁一个车位，到了直接停。`useDuration` 用分钟数记录使用时长，为计费提供基础事实。`reserve1` 这个备用字段在原项目里被复用为禁行/停用原因，车位维修、临时封场时，停用原因要能对业主讲清楚。

这个台账设计的核心张力在于：**车位是一个物理资源，但它的"占用"状态由系统推断**。车辆入场识别到车位被占、出场识别到释放，状态机跟随事件流转。这里有一个原项目没有显式处理、但生产环境一定会遇到的问题——**事件丢失导致的状态漂移**：道闸上报入场了，但对应的车位状态更新丢了（网络抖动、服务重启），台账就会慢慢偏离现实。我的补法是给状态机加了一个"对账"动作：每天凌晨用出入场流水重放一遍车位状态，发现漂移就修正并告警。台账是资源模型，流水是事实来源，两者不一致时信流水——这个原则和上一章讲门禁时"信流水"一脉相承。

## 账单生成：一段值得抄作业的事务代码

车位动了，账单就该来了。账单生成在 `ParkingPaymentServiceImpl` 里，这段原文我完整贴出来，它是整个停车模块里结构最标准的一段：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public ParkingPaymentGenerateRespVO generateParkingPayment(ParkingPaymentGenerateReqVO reqVO) {
    // 1. 构造 DO，写入车牌号、停车时长、费用金额
    ParkingPaymentDO entity = new ParkingPaymentDO();
    entity.setPlateNo(reqVO.getPlateNo());
    entity.setParkDuration(reqVO.getParkDuration());
    entity.setFeeAmount(reqVO.getFeeAmount());
    // 2. 初始状态：账单"待缴费"，发票"未开具"
    entity.setBillStatus("待缴费");
    entity.setInvoiceStatus("未开具");
    // 3. 生成账单编号: PP + yyyyMMddHHmmss + 4位随机数（如 PP202605181430251234）
    String billCode = "PP" + LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
            + String.format("%04d", (int) (Math.random() * 10000));
    entity.setBillCode(billCode);
    // 4. 写入数据库
    parkingPaymentMapper.insert(entity);
    // 5. 返回账单编号
    ParkingPaymentGenerateRespVO respVO = new ParkingPaymentGenerateRespVO();
    respVO.setSuccess(true);
    respVO.setBillCode(billCode);
    return respVO;
}
```

逐段读它的设计意图。

**初始状态一步到位**：账单一落库就带着"待缴费"和"未开具"两个状态，状态字段的初始值在生成方法里显式声明，而不是靠数据库默认值隐式兜底。这两种写法的差别在排查时就会显现：显式声明让"账单从哪里开始"这件事在代码里可读，后来者不需要去翻表结构猜默认值。

**账单编号的生成规则**很直白：`PP` 前缀加时间戳加四位随机数。这个编号是人可读的——拿到一张 PP202605181430251234，运营一眼能看出账单是 2026 年 5 月 18 日 14 点 30 分生成的，对账时按时间排查非常顺手。但我要直接指出它的局限：**四位随机数在并发下会撞**。同一秒内生成两万张以上账单时，生日问题会让重复概率快速上升；即便概率低，一旦撞上，如果 billCode 上有唯一索引，插入会失败。我的改造是换成了"时间戳加发号器"：时间戳保留可读性，随机段改成 Redis `INCR` 的当日序列，并发越高越不会重。账单号这个东西，宁可规则复杂一点，也不能在财务对账时出现重号。

**事务注解** `@Transactional(rollbackFor = Exception.class)` 是芋道代码的标配写法。默认的 `@Transactional` 只在 RuntimeException 和 Error 时回滚，受检异常不回滚——而账单生成如果后续要扩展出"落库成功再发短信"之类的多步逻辑，一个受检异常就可能造成"账单生成但关联动作丢失"的中间态。`rollbackFor = Exception.class` 把受检异常也纳入回滚，是防御性正确。我在代码评审里看到没有这个参数的事务注解，一律要求补上。

## 账单状态机：两条独立的线

账单的状态有两条线：`billStatus` 管支付（待缴费、已缴费、已欠费），`invoiceStatus` 管发票（未开具、已开具）。两条线独立演进，这是有意的拆分——**付没付钱**和**开没开发票**是两件业务上独立的事：先开票后付款（月结客户）和先付款后开票（临停）都合法，如果把它们捏成一个状态字段，就表达不出这种正交性。

`ParkingPaymentDO` 的关键字段在这里补齐：车牌号 `plateNo`、停车时长 `parkDuration`、费用金额 `feeAmount`，加上后面会用到的 `discountAmount`（优惠金额）、`discountReason`（优惠原因）、`payType`（支付方式）、`payTime`（支付时间）。注意车牌号又是冗余直存的——和上一章通行记录存姓名同理，账单要能独立于车辆档案自证。

## 月卡与临停：同一张表上的双轨生意

车位台账讲完，在进入账单之前，还有一个业务分层要交代：**月卡车位和临停车位是两种生意，但共享一张台账**。

月卡是 B 端生意：企业或个人按月购买固定车位，月底出账单，金额固定，争议少，重点是续约管理——到期前提醒续费，逾期未续自动把车位类型从"固定"释放回"临时"并同步车闸白名单。月卡的车闸放行依据是白名单（车牌库），车辆到达识别即放行，几乎无感。

临停是 C 端生意：按次计费、当场支付、离场放行，高频低额，重点是速度与准确性——识别、计费、支付、抬杆这条链路每多一秒，出口就多积一台车。临停的放行依据是支付凭证或离场豁免规则（比如 15 分钟内免费）。

原项目的 parking 三件套（parkingspace 台账、parkingmgmt 管理、parkingpayment 计费）把两条轨道放在一个模块里，靠 spaceType 与账单类型区分。我在二开时做的一件重要的事，是把两条轨道的**账单节奏**拆开：月卡按月批量出账（月初一个批处理任务为所有在租月卡生成账单），临停按次实时出账（车辆出场时生成）。批量出账任务跑在某天凌晨三点，失败有重跑机制；实时出账挂在出场事件后，要求毫秒级响应。同一个数据模型，两种调度形态，这条经验适用于一切"批发与零售并存"的收费业务。

月卡批处理还有个细节值得记：批量生成的账单号如果沿用"时间戳加随机"规则，同一秒内几千张账单必然撞号——第 5 章开头说的发号器方案，最早就是被月卡批处理逼出来的。批处理是并发问题的放大器，任何"单条看没事"的设计，都值得拿到批处理语境下再审一遍。

## 入场链路：时长从哪一刻开始算

账单上的 parkDuration 停车时长，起点是"入场时间"。这个时间从哪来？链路是：车辆驶入识别区 → 车牌识别相机抓拍识别 → 道闸放行 → 地磁或视频复核确认入场 → 事件上报平台落库。

这条链路上有个经典争议：**时长起点用"识别时间"还是"确认入场时间"？** 识别在前、确认在后，中间可能差几秒到几十秒（车主停顿、跟车、倒车重进）。用识别时间，车主可能多付几十秒的钱——没人会在意；用确认时间，遇到"识别了但最终没进"的车辆（掉头走了），就要处理没有落地的入场事件。原项目跟随事件上报时间，也就是识别放行的时间，这是实务派的选择：误差可忽略、事件完整、逻辑简单。我照单全收，但在出场侧做了对应的对齐——出场时长终点同样取事件时间，两头一致，争议最小。

真正需要精细处理的是**跟车与重复入场**：前车出场时识别相机可能把后车车牌一起识别了，产生"幽灵入场"；或者车辆在园区内多个出入口之间穿行，一天产生多次出入场事件。处理办法是入场事件的去重窗口（同一车牌 N 分钟内只认一次入场）加出场配对逻辑（最近一次未配对的入场事件作为本次出场的前驱）。这套配对逻辑写得朴素，但它是 parkDuration 准确性的守门人——时长错了，后面所有的 BigDecimal 精确都是白精确。

## 从车位到账单：为什么中间隔了一层

有读者可能会问：车辆出场识别到时长，直接算钱扣款不就完了，为什么要先生成一张"待缴费"的账单，再走缴费流程？

因为这个中间层承载了**对账与争议处理**。车辆出场时如果直接扣款，一旦金额有争议（设备把停留时间记错了、优惠政策没生效），钱已经扣了，处理起来就是退款流程，麻烦且伤体验。先生成账单，金额摆在明面上，扫码支付前用户看得见金额，有争议时账单停在"待缴费"，运营可以介入调整优惠。临停场景看似多了一步，实际上是把财务风险从"事后退款"挪到了"事前确认"。

这个"事实-账单-支付"三段式，是所有涉及收钱的业务系统的通用骨架：网约车的行程-账单-支付、物业的用量-账单-缴费，都是同一个形状。园区停车的特殊之处只在于高频与低额——单笔金额小、日单量大，所以这一章讲的账单生成要追求轻，下一章讲的计算与催缴要追求准。

## 唯一索引的坑：呼应第二章埋的伏笔

上一章讲逻辑删除时留了个钩子，在这里兑现：如果给 `bill_code` 建唯一索引，配合框架的逻辑删除（删除改写为 UPDATE deleted 标记），会出现一个隐蔽的问题——删除一张账单后，它的 billCode 还留在表里占着唯一索引，再次生成同号账单（时间戳同秒加撞随机数）就会插入失败。

解法有三种：唯一索引改成"逻辑删除字段参与"的复合唯一（PostgreSQL 里用部分索引 `WHERE deleted = false` 实现）；或者账单号生成规则本身就保证全局不重（发号器方案天然免疫）；或者干脆不允许删除账单——财务单据只冲正不删除，这也是财务系统的一般纪律。我采用了后两种的组合：发号器保证不重，账单禁删。原项目没有在这张表上做唯一索引，我加上索引时就把这些问题一并想清楚了。

顺带把 `parking_payment` 的索引策略也定下来，这是账单表上线前必须想清楚的：车牌号要建索引（车主查自己的账单走车牌）、`bill_status` 要建索引（催缴任务扫"待缴费超时"的账单是最重的定时查询）、`pay_time` 建索引（对账与统计按支付时间过滤）。三列各建单列索引，而不是拍脑袋建一个大而全的组合索引——账单表的查询方太多（车主端、运营端、财务端、统计端），组合索引讨好了一方就会拖累其余几方。单列索引在千万级以下的表上完全够用，这是"先简单后复杂"在索引设计上的应用。

车位与账单的骨架搭完了。下一章进入金额计算的核心：BigDecimal 为什么必须用、优惠减免怎么落库、催缴怎么把"待缴费"推成"已欠费"、以及态势统计的 SQL 怎么写。那是停车模块真正见功夫的地方。
