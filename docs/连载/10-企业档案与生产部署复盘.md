# 企业档案与生产部署复盘

收官这一章讲两件事：一是企业档案——它看起来是最平淡的模块，却是把前面九章所有业务线串起来的主数据枢纽；二是生产部署与全系列复盘，把这套平台从开发机搬到生产机的完整路径，和我在整个二开过程中沉淀的经验教训，一次讲完。

## enterprise_file：租户主数据的枢纽

企业档案落在 `enterprise_file` 表，`EnterpriseFileDO` 原文：

```java
@TableName("enterprise_file")
public class EnterpriseFileDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * 企业名称
     */
    private String enterpriseName;
    /**
     * 统一社会信用代码
     */
    private String creditCode;
    /**
     * 注册地址
     */
    private String registerAddr;
    /**
     * 企业类型
     */
    private String enterpriseType;
    /**
     * 企业规模
     */
    private String enterpriseScale;
    /**
     * 档案状态
     */
    private String fileStatus;
    /**
     * 员工总数
     */
    private Integer staffCount;
    /**
     * 审核人账号
     */
    private String checkUser;
    /**
     * 审核通过率
     */
    private BigDecimal checkRate;
    /**
     * 操作人账号
     */
    private String handleUser;
}
```

先讲它的枢纽地位。回头看前九章：门禁人脸库的 `company` 字段是企业名、访客预约的 `visitCompany` 是企业名、停车月卡的租用方是企业、能耗分摊的分摊主体是企业。企业档案就是这些散落引用的**锚点**——园区平台的租户主数据。

主数据管理最重要的一条是**唯一标识**。这个表用 `creditCode` 统一社会信用代码做企业的法定唯一键，这是对的：企业名称会改（更名、换品牌），信用代码不会。我在二开时给 creditCode 加了唯一约束（配合逻辑删除的部分索引），重名企业靠信用代码区分，档案合并、租户迁移这些脏活才有可靠的依据。

`fileStatus` 档案状态值得单独说。企业入驻园区不是一步到位的：意向入驻 → 提交资料 → 审核入驻 → 退租离园，档案状态跟随这个生命周期。`checkUser` 审核人和 `checkRate` 审核通过率挂在档案上，把"企业资料审核"这个动作显式建模——**园区的招商资料审核是有合规意义的动作**，谁审的、通过率多少（可以侧面反映资料质量或审核尺度），都留了痕。

`staffCount` 员工总数和 `staff_mgmt` 表（企业员工）联动。员工表的结构是主从关系的标准形态：

```java
@TableName("staff_mgmt")
public class StaffMgmtDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * 员工姓名
     */
    private String staffName;
    /**
     * 企业ID
     */
    private Long enterpriseId;
    /**
     * 所属部门
     */
    private String deptName;
    /**
     * 岗位
     */
    private String postName;
    /**
     * 权限状态
     */
    private String authStatus;
    /**
     * 通行区域
     */
    private String accessArea;
    /**
     * 授权人账号
     */
    private String authUser;
    /**
     * 操作人账号
     */
    private String handleUser;
}
```

`enterpriseId` 外键挂企业，`authStatus` 权限状态、`accessArea` 通行区域、`authUser` 授权人——这几个字段让员工表直接对接第 3 章的人脸库：员工入职时在企业服务里建档，审核授权后同步生成人脸库记录（授权区域、有效期一路带过去），员工离职停用权限，人脸库对应记录同步过期。**企业服务的员工管理是"人的授权源头"，门禁只是"人的授权执行端"**，这个职责划分定下来，前面第 3 章我讲的"每天凌晨刷过期权限"的定时任务就有了明确的上游——源头状态变更驱动同步，定时任务只是兜底。

主数据域还有一个绕不开的话题：**企业档案与租户体系的关系**。第 2 章讲的 framework 多租户是技术隔离（tenant_id 数据隔离），企业档案是业务身份（入驻园区的企业实体），两者不是一回事，但经常被混为一谈。我的划分标准是：一套部署服务一个园区的运营方（tenant_id 唯一），园区内的入驻企业全部落在企业档案里——同一租户下有几百个企业档案。如果未来平台化（SaaS 化）服务多个园区，tenant_id 升格为园区隔离，企业档案仍然是租户内的业务主数据。层次分清楚，两种"租户"才不会在代码里打架。

企业档案的另一个实战功能是**退租清算的锚点**。企业退租时，系统要做一次全链路清算：门禁权限回收（人脸过期）、车位租约终止（第 5 章的月卡释放）、能耗分摊止算（当月按天折算）、历史账单催缴清零。清算清单的每一项都挂在企业 ID 下，这就是主数据作为锚点的价值——注销一个企业，系统能自动列出所有需要处理的关联项，运营逐项打勾，不靠记忆。

## 生产部署：六个服务的编排

全系列讲的都是代码，最后把部署 topology 收拾干净。生产环境的部署清单：

**基础设施层**：MySQL（业务库，所有模块共库分表，PostgreSQL 部署时靠第 2 章讲的 KeySequence 适配）、Redis（缓存、会话、发布订阅通道）、Nacos（注册中心与配置中心）。

**平台服务层**：Gateway（唯一对外入口，HTTPS 终结在网关）、system 服务（用户权限租户）、infra 服务（文件、定时任务、API 日志）。

**业务服务层**：industrialpark 服务（四个子模块打成一个部署单元）。

配置管理的纪律是：**所有环境相关的值走 Nacos 配置中心，代码里的 yml 只留本地开发的默认值**。数据库连接、Redis 地址、第三方密钥全部下沉到 Nacos 的命名空间里，按 dev/prod 隔离。发布流程相应变得极简：改配置去 Nacos 控制台动态刷新，改代码走构建发布——两者彻底分离。

定时任务是这套平台的隐形骨架，前面各章都出现过：权限过期刷新（第 3 章）、车位状态对账（第 5 章）、能耗采集调度（第 7 章）、访客在园核查（第 4 章）。它们全部注册在 infra 的任务中心，cron 表达式可视化管理，执行日志可查。生产事故里定时任务默默挂掉是高发场景，任务中心的执行记录是排查的第一现场。

上线前我做的一件重要的事是**容量预判**：按园区规模（几百路摄像头、几百块表、几千个车位、日均几千条通行）估算各表的年增量，为 access_record 和 energy_collect 这两张大表预留分区方案（按月分区），账单表按年归档。上线时这些表还小，但分区策略先定下来，避免一年后在线改表的历史难题。

## 上线清单：从"能跑"到"敢用"

部署拓扑搭好只是"能跑"，生产验收前我按一份 checklist 逐项打勾，这里把单子留给读者——每一条背后都是一次真实的教训或惊吓。

**数据初始化核对**：企业档案、车位台账、设备台账三份主数据的初始导入，逐表核对总数与抽样明细。主数据错一条，下游全错——车位台账错一个编号，账单就会挂到不存在的车位上。

**权限矩阵走查**：按角色（园区管理员、安保、物业工程、财务、企业租户管理员）逐一登录走查菜单与接口权限。第 2 章说的"权限串第一公民"在这里兑现：每个角色的可见菜单、可操作动作逐项打勾，重点验证租户隔离——A 园区的账号能不能看到 B 园区的数据？答案必须是断然的"不能"。

**定时任务逐个手动触发**：权限过期刷新、车位对账、能耗汇总、访客核查、对账任务——全部在测试环境手动触发跑一遍并检查产出。上线后它们凌晨三点才跑，不能等到第一周凌晨才发现 cron 表达式写错。

**支付链路全真演练**：沙箱环境走完"出账-支付-回调-对账"全流程，再故意模拟回调丢失（拦截回调报文），验证对账任务能发现差异。钱链路上的每一个"应该"，都要有一个"验证过"。

**备份与恢复演练**：数据库全量备份加 binlog 增量的策略配好后，真实做一次恢复演练——备份没恢复过的等于没有备份。演练同时记录恢复耗时，它是你判断 RTO 目标能否达成的唯一依据。

**监控告警接通**：服务探活、接口错误率、数据库连接池、磁盘水位、定时任务执行状态——五个基础监控项接通知渠道（企业 IM 或短信）。监控的原则是"宁可扰梦，不可漏报"，前两周的告警噪音通过调阈值收敛，而不是一开始就静音。

这份清单走完通常要三到五天，有人嫌慢。但上线事故的修复成本是清单成本的十倍起，而且事故赔进去的还有信任——园区平台的服务对象是几十家入驻企业，第一次印象分掉下去，后面要还很久。

## 灰度、回滚与运维的日常

正式切流我采用的不是一次性切换，而是**业务灰度**：第一周只开放门禁与访客（高频但低风险，出问题影响的是体验不是钱），第二周加停车计费（开始碰钱，对账任务重点盯），第三周加能耗与安防（数据积累类业务，风险最低）。每一步灰度都预设了回滚预案：网关注册的模块服务可以随时摘除，摘除期间对应业务线下运转（园区当然有应急预案——纸质登记、人工收费），平台数据靠补录兜底。灰度的顺序原则是：**先上不碰钱的，再上碰钱的；先上可线下替代的，再上离不开系统的**。

运维日常里我印象最深的两个场景，值得写给后来者。一个是一次告警风暴：某天上午告警队列瞬间涌入上千条，排查发现是一台边缘网关重连后重发了积压事件——从此所有事件接口都加了幂等键（设备侧事件序号），重发不再产生重复数据。另一个是一次"幽灵欠费"：财务反映某企业有笔账单一直欠费，但对方坚称已扫码支付——排查发现支付回调验签失败被拒收（对方支付渠道变更了证书），钱在渠道侧、状态在平台侧，对账任务第二天的差异明细精准抓出了这笔。事后我把回调验签失败的场景加进了监控告警，这类问题从"财务找上门"变成"系统先知道"。

这两个场景的共同教训是：**生产系统的可靠性不在架构图上，在幂等、对账、告警这些不起眼的细节里**。架构图决定系统能不能跑，细节决定它跑多久。

## 复盘：二开开源项目的六条心得

十篇文章写完，最后把整个二开过程的复盘收拢成六条，它们不是园区的业务知识，是做任何开源二开项目都适用的方法论。

**一、选型看代码，不看 README。** 本系列第 1 章的候选评估里，两千 star 的项目是壳仓库，零 star 的项目结构反而清晰。判断依据永远是：DDL 是否完整、Service 实现是否落地、提交历史是否持续。README 是广告，代码是体检报告。

**二、先跑通最小子集，再谈全量。** 智慧城市全家桶里我只启用了五个服务。二开的第一周就把最小可运行组合（Nacos + Gateway + system + 目标模块）跑通，之后所有开发都在这个子集上进行——快速反馈闭环的价值，远大于"先把全景跑起来"的满足感。

**三、顺着原作者的约定写代码，别耍个性。** 六层结构、状态字段用字符串枚举、字典化、审计字段自动化——这些约定有的不合我的口味，但我全盘继承。二开项目最大的维护成本是"两套风格打架"，新代码越贴近原约定，未来升级合并的成本越低。真要推翻某个约定，就彻底推翻并全量迁移，最忌讳同一层里两种风格并存。

**四、事实与派生分离，冗余要有语义。** 通行记录冗余姓名（流水快照语义）、实付金额不落库（可推导）、表底数落库（设备事实）、区间用量不落库（派生值）。每存一个字段都问一句：这是事实还是派生？冗余的语义是什么？答不上来的字段，半年后就是没人敢动的谜团。

**五、状态机是园区业务的第一模型。** 访客五态、车位三态、账单双线、告警两维——园区平台几乎每个模块的核心都是一张状态机。状态字段用单字段互斥枚举，迁移动作收敛在 Service 方法里，一次方法调用一次迁移。状态机清晰了，统计、对账、异常处置全都是顺带的产品。

**六、生产化的差距在"边角"上。** 原项目的业务骨架搭得很好，但生产化欠缺的全是边角：账单号的并发安全、凭证核销的有效性校验、采集空洞的补数、设备离线告警、定时任务对账。这些边角在 demo 里全部隐形，在运营第二个月开始全部现形。二开的价值恰恰在这里——**开源项目给你骨架，生产运营逼你补肉**，而连载里每一章我修的那些洞，就是这段补肉过程的全记录。

## 写在最后

这个系列从选型讲到部署，主线始终是一个：把 genchuan-smart-city 的产业园区模块改造成贴合自己园区的平台。开源二开不是偷懒，而是站在一个经过生产验证的骨架上，把自己的业务规则、数据口径、运维经验装进去。改造的过程里，读懂别人的代码和想清楚自己的业务，各占一半时间——而这两件事的收获，都会沉淀成你下一次面对新系统时的底气。

十个章节、四条业务线（门禁访客、停车计费、能耗监测、综合安防）、一个主数据枢纽（企业档案），到这里全部讲完。希望这条从选型到上线的完整路径，能帮到正在做类似项目的你。
