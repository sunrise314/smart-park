# 综合安防：视频监控与实时告警

综合安防是园区平台里实时性要求最苛刻的一条业务线：门禁晚三秒是体验问题，告警晚三秒可能就是事故。原项目的安防域收敛在 integratedsecurity 子模块里，规模不大（十几个文件），但把"设备-画面-告警-处置"的骨架搭完整了。这一章讲它的数据模型与告警链路，以及我在二开时对"实时"二字做的工程化改造。

## real_time_monitor：一张表上的监控台账

安防域的核心数据对象是 `RealTimeMonitorDO`，对应 `real_time_monitor` 表，原文：

```java
@TableName("real_time_monitor")
public class RealTimeMonitorDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * 摄像头ID 关联camera_mgmt表id
     */
    private Long cameraId;
    /**
     * 摄像头名称
     */
    private String cameraName;
    /**
     * 安装区域
     */
    private String area;
    /**
     * 运行状态：正常/异常 关联字典：real_time_monitor_run_status
     */
    private String runStatus;
    /**
     * 告警状态：无告警/告警中 关联字典：real_time_monitor_alarm_status
     */
    private String alarmStatus;
    /**
     * 监控画面地址
     */
    private String imgUrl;
    /**
     * 经度
     */
    private BigDecimal lon;
    /**
     * 纬度
     */
    private BigDecimal lat;
    /**
     * 告警内容
     */
    private String alarmContent;
    /**
     * 操作人账号 关联芋道用户表
     */
    private String handleUser;
    /**
     * 处置结果
     */
    private String handleResult;
    /**
     * 截图记录
     */
    private String snapImg;
}
```

这张表最值得学的设计是**两个状态的解耦**：`runStatus`（运行状态：正常/异常）管设备健康，`alarmStatus`（告警状态：无告警/告警中）管业务事件。这两个维度正交——设备运行正常但告警中（摄像头好好的，拍到了入侵）合法；设备异常且无告警（摄像头掉线了）也合法，而且后者本身就是一类必须处理的告警（设备离线告警）。如果捏成一个状态字段，"设备离线"和"拍到异常"就互相污染，运维和安保的职责边界也糊了。

注意这两个字段的注释里都写了"关联字典"——芋道框架的字典机制。状态枚举值不硬编码在代码里，而是挂在系统字典下（`real_time_monitor_run_status`、`real_time_monitor_alarm_status`），前端下拉框、后端校验、报表翻译统一从字典取。二开时我给告警状态扩展了第三态"已确认处理中"，只是加了一个字典项加一段迁移逻辑，没有动表结构——这就是字典化的好处：**枚举演进不动表**。

**位置字段（`lon`/`lat`）**用 BigDecimal 存经纬度，安防摄像头在园区地图上按坐标落点，告警触发时值班员能在地图上直接看到"哪个位置出的事"。经纬度用 BigDecimal 而不是 double 同样是精度纪律——坐标差万分之三度在地图上就是几十米，告警点位标注差几十米，安保白跑一趟。

**处置闭环三件套**：`alarmContent` 告警内容、`handleResult` 处置结果、`snapImg` 截图记录。加上第 3 章通行记录里的核查三字段，你会发现园区平台的异常处置都长一个样：**事件 → 证据（截图/抓拍）→ 结论（处置结果）**。证据先行是这个模型最重要的一环——告警只有一句话，处置就没有依据；先落截图，值班员在处置前有现场可看，事后有据可查。

## 告警链路：从画面到工单的流转

把链路走一遍。摄像头接入层（videomonitor 包）负责设备注册与画面流管理，`camera_mgmt` 表维护摄像头档案，`real_time_monitor` 维护运行快照。事件侧的链路是：

1. **事件产生**：智能分析（周界入侵、区域滞留）或人工值守发现异常，产生告警事件，附截图；
2. **落库推流**：告警写入 `real_time_monitor`（alarmStatus 置"告警中"、alarmContent 写内容、snapImg 存截图路径），同时通过站内信或企业 IM 推送值班端；
3. **人工处置**：值班员调看监控画面（imgUrl）与截图，处置后写 handleResult；
4. **闭环归档**：告警状态翻回"无告警"，处置记录留档。

这条链路的工程要害在第 2 步——"推"。轮询数据库做告警通知是能跑的，但秒级轮询空转浪费、分钟级轮询告警延迟又不可接受。原项目在集成监控时使用了服务间调用与消息通道的组合，我二开时的最终形态是：告警事件先落库（事实优先），再通过 Redis 发布订阅通知值班端（推送解耦），值班端收到通知再拉取详情。**先落库后推送**的顺序不能反——推送丢失可以补看，落库丢了告警就消失了。

## "实时"的工程代价与我的取舍

"实时监控"这个词在产品语境里很轻，在工程语境里很重。完全的实时（毫秒级）意味着 WebSocket 长连接全量推送，服务端要维持连接、处理重连、压测消息风暴——对一个园区的告警量级（日均几十到几百条）来说是杀鸡用牛刀。

我的取舍是把"实时"拆成两档：

**告警是推送实时**。告警事件发生，推送通道秒级送达值班端。这个量级（每分钟个位数消息）用 Redis 发布订阅绰绰有余，不需要专门的消息中间件。

**画面是轮询准实时**。监控列表页的运行状态、最新截图，用 10 秒轮询刷新。图片流本身走摄像头 NVR 的流媒体服务，平台只管地址（imgUrl 存的是流媒体取流地址），不代理视频流——**平台绝不背视频流量的锅**，这是安防集成的一条铁律，视频流的带宽和并发是业务系统服务器扛不住的。

这个组合让 integratedsecurity 服务变成了一个轻量服务：数据层是两张表加字典，推送是一个 Redis 通道，视频是外链。整个子模块十几个文件就够用，这也是它代码量在四个子模块里最小的原因——不是设计得少，是职责收得窄。

再补一个生产化的硬环节：**告警风暴的抑制**。监控域有一种事故叫告警风暴——一台智能分析服务误配置，对同一路画面每秒生成一条"区域入侵"告警，几分钟内就能把告警表灌进上万行，值班端的推送队列跟着雪崩。我的防线有三层：同点位同类告警的抑制窗口（五分钟内重复事件只更新计数不新开告警）、告警速率熔断（单点位每分钟超过阈值自动转入"疑似异常源"静默区并通知运维）、风暴后的合并降噪（风暴期间的重复告警合并成一条摘要）。安防系统的可用性指标里，"告警的可信度"和"告警的时效性"同等重要——狼来了喊多了，真狼来的时候没人抬头。

## 摄像头接入：协议与存储的两笔账

视频监控接入的第一件事是搞清楚协议账。园区存量摄像头的主流接入路径有两条：**GB/T 28181**（国标联网协议，政府背景项目的标配，信令走 SIP、流走 RTP）和 **RTSP 直取**（老牌私有路径，直接从设备或 NVR 拉流）。原项目在 camera_mgmt 档案之上做平台侧接入，我二开时的选型原则很简单：有 NVR 的园区一律从 NVR 取流（集中管理、天然录像回放），没有 NVR 的少数点位用国标接入——平台侧只维护"取流地址怎么拼"的适配逻辑。

存储是第二笔账，也是预算大头。监控录像存储在 NVR 或磁盘阵列上，平台不存视频流——这条在本章开头就立了规矩。平台真正要存的是**事件证据**：告警截图、告警前后的短录像片段。我的设计是告警落库时同步从录像流截取事件片段（前后各十五秒）转存到文件服务，表里存路径。这样即使 NVR 按周期循环覆盖了录像，关键事件的证据链依然完整保全——监控录像一个月就覆盖，但一次事故的证据要留到处理完毕加申诉期结束，两者生命周期完全不同，必须分开管理。

这笔账算下来，平台侧的存储压力很小（每天只有事件片段），NVR 侧按路数和码率算容量（1080p 主码流一路一天约 20G，配 16 盘位阵列可以保 30 天以上）。存储规划要在选型阶段就做，上线后才发现"录像只保了七天"这种事，会直接击穿安防项目的验收底线。

## 隐私与合规：安防系统的隐形边界

视频监控天然涉个人信息，合规设计不是选修课。我在二开时落实了几条硬约束，这里如实列出，做同类项目的朋友可以直接参考。

**最小可见**：监控画面的查看权限按区域分配，值班员只看职责范围内的点位；所有取流与截图动作记录操作日志（谁、何时、看了哪个点位）。平台页面禁用下载按钮是不够的，关键是日志与审计让每一次查看可追溯。

**告警截图的脱敏与期限**：告警截图里可能拍到无关人员的清晰面孔，默认保留期限设为 90 天，到期自动清理；涉及事件处置的截图随事件档案延长保留，随案不随期。

**人脸数据分离**：第 3 章人脸库的照片属于生物识别信息（个人信息保护法里的敏感个人信息的处理要求单独同意与更严保护），存取链路独立于普通业务库，访问走单独的权限点。员工入职采集人脸时的告知同意书，是系统里录入人脸的前置校验项——同意书编号录不进去，人脸就录不进去。

这些约束的实现成本都不高，但它们决定了平台能不能在法务和业主审查下站住。技术人常有个误区，觉得合规是法务的事——在数据平台上，合规一半是表结构和权限设计的事，而那正是我们的事。

## 值班工作台：把告警变成流程

原项目的告警处置是"列表加详情"的管理端形态，我把它升级成了值班工作台，围绕值班员的实际作业流重组：左侧是待处置告警队列（按严重度排序、新告警置顶闪动），中间是选中告警的现场信息（点位地图、实时画面、事件截图、关联的通行记录），右侧是处置表单（处置动作模板、备注、升级按钮）。

工作台有两个刻意的设计。**一是处置动作模板化**：误报已排除、现场已核实无异常、已劝离、已上报上级——值班员点选而不是打字，处置效率高且口径统一，月度处置报告直接按模板统计。**二是升级机制**：超过时限未处置的告警自动升级提醒（先提醒值班员，再提醒安保主管），严重告警（如消防通道占用）跳过提醒直接升级。升级链路的本质是把"告警被看到了"变成"告警被承诺了"。

工作台还补了一个原项目没有的小功能：**交接班视图**。值班交接时，未闭环的告警、待核查的异常通行、在园访客异常，一屏列给下一班。安保是 24 小时轮转的，系统的责任交接也要跟着轮转——这个视图现在成了值班交接的仪式性页面。

## 与门禁的联动：安防的下半场

单看摄像头，安防域是"看到异常"；和门禁联动之后，才能"看懂异常"。两个最有价值的联动场景，我在二开时都做了：

**一是陌生人脸与视频联动**。第 3 章的通行记录里，`accessStatus` 拒绝状态的记录如果同时命中了摄像头覆盖区域，安防端自动把该摄像头的实时画面顶到值班界面，值班员直接目视确认。门禁给了"谁被拒了"，视频给了"现场长什么样"，两个系统各出一半信息，合成一个可决策的场景。

**二是离园核销与滞留告警**。第 4 章访客生命周期里"已到访未离园"的在园名单，超过预约离园时间仍在园的访客，联动其到访区域的摄像头做一次画面抽查。大多数滞留只是访客忘了登记离园，但这个低成本的核查动作，把"名单可信度"从纸面落到了地面。

安防这一章讲的与其说是技术，不如说是"职责纪律"：设备健康与业务告警分开、事实落库与推送通知分序、视频流量与业务系统分家。下一章是本系列的收官：企业档案与员工管理怎么把前面所有业务线串成主数据，以及整个平台的生产部署与我的复盘。九个章节的伏笔，最后一章全部收线。
