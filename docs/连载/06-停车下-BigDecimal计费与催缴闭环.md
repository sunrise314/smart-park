# 停车下：BigDecimal计费与催缴闭环

上一章搭好了车位台账和账单生成的骨架，这一章进入停车模块的心脏：金额计算、优惠减免、缴费与催缴，最后落在态势统计。这些环节单看每个都不复杂，合起来构成了一条财务闭环——而财务闭环里最不能出现的东西，是"差一分钱对不上账"。

## BigDecimal：金额计算的底线

先看费用计算的原文实现：

```java
@Override
public ParkingPaymentCalculateRespVO calculateParkingPayment(ParkingPaymentCalculateReqVO reqVO) {
    // 1. 校验账单存在
    ParkingPaymentDO entity = parkingPaymentMapper.selectById(reqVO.getId());
    if (entity == null) {
        throw exception(PARKING_PAYMENT_NOT_EXISTS);
    }
    // 2. 计算费用明细：原始费用 → 优惠费用（默认0） → 实付费用 = 原始 - 优惠
    ParkingPaymentCalculateRespVO respVO = new ParkingPaymentCalculateRespVO();
    respVO.setOriginalFee(entity.getFeeAmount());
    BigDecimal discountFee = entity.getDiscountAmount() != null ? entity.getDiscountAmount() : BigDecimal.ZERO;
    respVO.setDiscountFee(discountFee);
    respVO.setActualFee(entity.getFeeAmount().subtract(discountFee));
    return respVO;
}
```

短短十几行，有三个细节值得逐个讲。

**第一，金额字段全部用 BigDecimal，`DO` 里的 `feeAmount`、`discountAmount` 都是**。这是 Java 金额处理的铁律：double 和 float 是二进制浮点，表示不了 0.1 这样的十进制小数，`0.1 + 0.2` 在浮点世界里是 `0.30000000000000004`。停车计费里这种误差的单次影响可能只有几厘，但园区一天几千笔账单、财务月底对总账时，误差会以"账实不符"的形式炸出来，而且极难排查。BigDecimal 是十进制精确表示，加减乘除都是确定性的。数据库侧对应的是 `DECIMAL` 类型而不是 `FLOAT/DOUBLE`——字段类型和 Java 类型要在同一个精度世界里，这一点在写 DDL 时就要定死。

**第二，空值防御写在了计算之前**。`entity.getDiscountAmount() != null ? ... : BigDecimal.ZERO`——优惠金额字段允许为空（大多数账单没有优惠），计算前把空值归零。这个写法看似啰嗦，却避免了一个真实的坑：BigDecimal 的算术运算遇到 null 直接抛 NPE，一条没有优惠的账单查费用明细直接 500，这种问题测试环境经常测不出来，因为测试数据总是"填得满满的"。

**第三，实付 = 原始 - 优惠的推导关系是"算出来的"，不是"存出来的"**。注意 `actualFee` 只出现在响应 VO 里，DO 表里并没有这个字段——实付金额永远是计算的结果，不落库。这个决策保证了数据一致性：优惠金额改了，实付自动跟着对，不存在"优惠改了但实付忘了重算"的脏数据。凡是能从其他字段推导出来的值，一律不落库，这是关系建模的一条基本纪律。当然它也有代价：统计实付总额时要用表达式而不是直接 SUM 字段，这是可以接受的取舍。

## 优惠减免：钱可以少收，原因必须留下

优惠减免的实现很直接：`discountParkingPayment` 把优惠金额和优惠原因写进账单。关键在 `discountReason` 这个字段——**减免金额必须伴随减免原因**，这不是产品要求，是内控要求。

园区的停车优惠场景很多：招商期给新租户免费停车、大型活动临时减免、设备故障导致计费失真的补偿。每一种优惠背后都应该有一个可追溯的业务依据。如果只记金额不记原因，半年后审计问"这批账单为什么少收了钱"，没人答得上来。我在二开时把优惠原因做成必填校验，并且把"谁批准的减免"也记了下来（复用 handleUser 的思路），优惠审批的留痕链条就完整了。

催缴和补缴是优惠的反面。`remindParkingPayment` 把超时未缴的账单推成"已欠费"，`repairParkingPayment` 则是欠费后的补缴——重新记录支付方式与时间，状态拉回"已缴费"。这两个方法一推一拉，构成欠费管理的闭环。

催缴的触发时机值得单独设计。原实现是人工点击触发，我改成定时任务加规则：临停账单超过 24 小时未缴进入催缴，月卡账单出账 7 天未缴进入催缴，催缴消息带账单链接直接推给车主（短信或小程序订阅消息）。催缴要有节制——同一账单的催缴间隔不少于三天，连续两次未响应转人工跟进。催缴过度是骚扰，催缴不足是坏账，这个节奏参数应该在运营后台可配置，让一线运营用真实反馈去校准。

补缴还有一个隐蔽的业务分支：**部分欠费的合并补缴**。车主有多张欠费账单时（月卡加临停混合使用的常见状况），逐张支付体验很差。我加了"合并补缴"入口：选定车主名下所有欠费账单，一次支付逐张核销——支付金额与账单合计严格相等，核销按账单创建顺序逐张落 `payTime`。合并支付在支付渠道侧是一笔流水，在账单侧是多张账单的核销，这个"一笔对多张"的映射关系要对账任务说清楚（支付流水号冗余到每张账单上），否则对账脚本会把一笔支付误判成多张差异。

## 缴费支付：状态迁移的最小实现

缴费方法 `payParkingPayment` 的原文骨架是：校验账单存在 → 记录支付方式 → 记录支付时间 → 状态改为"已缴费" → 返回支付链接。有意思的是那个返回的 `payUrl`（形如 `https://pay.example.com/parking/账单号`），原项目在这里返回的是一个示意性的支付链接。真正的生产改造中，这一步要接入真实的支付渠道（微信、支付宝或聚合支付），而接入支付后这个方法的重心会从"改状态"变成"处理回调"——支付平台异步通知才是支付成功的最终事实，`payTime` 与状态更新应该发生在回调处理里，而不是用户点下支付按钮的时刻。

我在二开时按照"回调为准"重排了这段逻辑：点支付只是创建支付单，回调验签通过才落 `payTime`、改状态。多了一层回调验签和幂等处理（同一笔回调可能重推），代码长了一倍，但账和钱终于是同一时刻的事实。这段经验在第 10 章部署复盘时还会再提。

## 态势统计：一段 SQL 顶十段 Java

停车模块的收尾是态势统计 `getParkingPaymentChart`，原文：

```java
@Override
public ParkingPaymentChartRespVO getParkingPaymentChart(Long startTime, Long endTime) {
    // 1. 查询卡片统计数据（总支付笔数/欠费笔数/总收入/缴费率），若为空则默认 0 防止 NPE
    ParkingPaymentChartRespVO chartVO = parkingPaymentMapper.selectCardStats(startTime, endTime);
    if (chartVO == null) {
        chartVO = new ParkingPaymentChartRespVO();
        chartVO.setTotalPay(0);
        chartVO.setArrearsCount(0);
        chartVO.setTotalIncome(BigDecimal.ZERO);
        chartVO.setPayRate(BigDecimal.ZERO);
    }
    // 2. 补充两个趋势维度：每日收入趋势 + 每日支付笔数趋势
    chartVO.setDayIncomeList(parkingPaymentMapper.selectDayIncomeList(startTime, endTime));
    chartVO.setDayPayList(parkingPaymentMapper.selectDayPayList(startTime, endTime));
    return chartVO;
}
```

这段代码有两个值得学的姿势。

**统计下推到 SQL**。卡片统计（总支付笔数、欠费笔数、总收入、缴费率）在 Mapper 里用一条聚合 SQL 完成，而不是把时间范围内的账单全捞到 Java 里循环算。缴费率这类"两个聚合值的比值"在 SQL 里就是一个除法表达式，让数据库做它擅长的事。配合按 `pay_time` 范围查询的索引，大表上的统计依然能维持毫秒级。

**空结果防御**。统计区间内一笔账单都没有时，聚合 SQL 返回一行全 NULL（COUNT 是 0，SUM 是 NULL），映射成 VO 就是全空对象。原项目在 Java 侧补了默认值——笔数归零、金额用 `BigDecimal.ZERO`。这个防御放在网关层的意义是：看板接口永远返回完整结构，前端不需要处理字段缺失。

我给这段统计加的一个东西是**缓存**。态势看板是园区领导每天打开频率最高的页面，但它的数据变化频率其实很低（分钟级）。我用 infra 模块的缓存能力给统计结果套了一层短 TTL 缓存（60 秒），支付回调成功时主动失效。看板打开速度从秒级进到毫秒级，数据库的聚合压力也卸掉了。

## 计费规则引擎：把"多少钱"从代码里解放出来

第 6 章贴的 calculateParkingPayment 是"算优惠后的实付"，但**原始费用怎么来的**没有展开——这正是计费规则的地盘，也是原项目留白最多、我二开用力最深的地方。

园区停车的计费规则花样繁多：首小时 5 元、之后每小时 2 元；30 分钟内免费；每日封顶 30 元；月卡车辆免费；新能源车位前两小时减免。如果把这些规则写成 if-else 硬编码在 Service 里，运营每调整一次定价都要发版——定价是运营策略，不是代码逻辑。

我的改造是把规则抽成配置化的**计费规则引擎**，数据模型三张表：

- 计费方案表：一个园区的定价方案（免费时长、首段单价、首段时长、续段单价、计价单位、日封顶、封顶口径）；
- 车型/车位类型映射表：不同车型（小型、大型）或车位类型（临停、预约）挂不同方案；
- 方案版本表：每次调价生成新版本并记录生效时间——历史账单必须按"当时生效的版本"计费，这是对账的法律基础。

计算过程纯函数化：输入（入场时间、出场时间、方案版本）输出（费用明细），不读库不写库。纯函数的好处是**可测试与可重放**：计费争议时，用历史版本对同一对时间戳重算一遍，结果与账单一比对，谁对谁错当场分晓。我给这个计算函数写了几十组单元测试，覆盖跨天、跨免费时段、整点边界（恰好 60 分钟算一小时还是免单）这些最容易扯皮的边界。

## 跨天与封顶：边界处的计费哲学

规则引擎里有两个经典的边界问题，单独拎出来讲，因为它们的答案体现计费系统的价值观。

**跨天怎么算？** 车辆晚上十点入场、次日八点出场，横跨两个计费日。做法有"按自然日重置"（次日重新起算免费时长与首小时）和"按连续时长计算"（一路算到出场）。两种都合法，但**必须在方案里显式配置**，园区 A 选按天、园区 B 选连续，同一辆车同一时长费用完全不同。隐性默认值是计费争议的温床——所有边界规则必须显式落库，这是规则引擎设计的第一原则。

**封顶口径怎么定？** 日封顶 30 元，封的是"自然日内累计"还是"单次停车"？月卡封顶、新能源封顶叠加时谁先谁后？我的落地是单次停车封顶优先（简单直观），多重优惠取最惠不叠加（可以少收，不能倒贴）。同样，口径写进方案配置并展示在缴费页——用户看得懂规则，争议自然少。

这两个边界问题没有标准答案，只有"明示的答案"。计费系统做的是信任生意，规则透明比规则优惠更能减少纠纷。

## 对账：给钱袋子上的最后一道锁

停车模块的所有环节都跑通之后，还有最后一道工序：**对账**。三方数据每天必须核对：平台账单（应收）、支付渠道流水（实收，从支付回调汇总）、车位出入场记录（应计）。三者的差异各有来源——账单生成后未支付（在"待缴费"正常挂着）、支付成功但回调丢失（实收多于已确认）、识别异常导致的漏计。对账任务每天凌晨跑，差异明细生成待办推给财务，人只处理机器对不平的部分。

对账这个环节在原项目里不存在，但只要平台碰钱，它就不是可选项。它也是前面所有工程纪律的最终受益者：账单号全局唯一（第 5 章）、支付以回调为准（本章）、金额全程 BigDecimal——三个纪律凑齐，对账脚本的逻辑可以短到三百行；缺了任何一个，对账脚本会膨胀成一个永远修不完的补丁堆。

## 停车两章的小结

把两章连起来看，停车模块的完整骨架是：车位台账（资源）→ 出入场事件（事实）→ 账单（责任凭证）→ 规则引擎与计算（BigDecimal 精确）→ 缴费（回调为准）→ 催缴与补缴（闭环）→ 对账（兜底）→ 统计（SQL 聚合加缓存）。这条链上每一步的设计决策，都在"高频低额"这个业务特征下做出的：账单生成要轻、计算要准、催缴要自动化、对账要日清、统计要缓存。

下一章切换赛道，讲能耗采集——电表水表的数据怎么进来、采集异常怎么治理。那是另一类完全不同的问题：不再是钱和状态机，而是高频时序数据和设备协议。
