# 访客预约：五状态生命周期

上一章的门禁模型管的是"内部人"，这一章管"外部人"。访客是园区里最不可控的人员类型：不熟悉路线、没有固定权限、随行人数不定，还要防备陌生人混进去的风险。原项目用一张 `visitor_appoint` 表加一套九个业务方法的 Service，撑起了一条"预约-审核-核销-离园"的完整生命周期。这一章我把这个状态机逐段拆开讲，这是整个园区模块里我最欣赏的一段设计。

## 先看状态：五个状态就是一条时间线

`VisitorAppointDO` 的字段上一章开篇已经完整贴过，这里只把关键的状态字段拎出来：

```java
/**
 * [预约状态] 如:待审核/已通过/已驳回/已取消/已离园
 */
private String appointStatus;
/**
 * [通行凭证] 审核通过后生成的通行凭证号
 */
private String ticket;
/**
 * [到达时间] 实际到达时间
 */
private LocalDateTime arriveTime;
/**
 * [离开时间] 实际离园时间
 */
private LocalDateTime leaveTime;
```

五个状态用文字枚举直接存在字符串字段里：**待审核、已通过、已驳回、已取消、已离园**。配套的四个字段把时间线钉牢：`visitTime` 是预约的到访时间（起点承诺），`arriveTime` 是实际到达（起点事实），`leaveTime` 是实际离园（终点事实），`ticket` 是审核通过后签发的通行凭证——线下闸机核销就认它。

时间线画出来是这样的：访客提交预约（待审核）→ 被访企业或园区运营审核（已通过 / 已驳回）→ 访客到园、出示凭证、闸机核销（arriveTime 落值）→ 办完事离开（leaveTime 落值、状态进入已离园）。任何在"已通过"之前的时点，访客或运营都可以取消（已取消）。

为什么我要专门花笔墨讲这条状态线？因为**状态机的设计质量，决定了这个功能运营起来的顺畅程度**。我见过把"是否审核通过"做成布尔字段、把"是否到访"又做一个布尔的实现——那不是状态机，那是字段拼图，查询"今天所有已通过但还没到访的访客"要拼三个条件，而且任何两个布尔组合出的非法状态（审核未通过却已到访）数据库都拦不住。原项目用一个字段表达互斥状态，配合 Service 层的状态迁移校验，非法状态在入口就被挡住了。

## Service 层：九个方法各司其职

`VisitorAppointServiceImpl` 的方法签名我完整数过一遍，除了分页、详情、导出这些标配，核心业务方法是六个：`createVisitorAppoint`（创建预约）、`auditVisitorAppoint`（审核通过）、`rejectVisitorAppoint`（驳回）、`verifyVisitorAppoint`（凭证核销）、`cancelVisitorAppoint`（取消）、`leaveVisitorAppoint`（离园登记）。

一个方法只做一次状态迁移，这是这套设计的纪律。我把核销方法的原文贴出来，这是整条链路上最关键的一环——它连接着线上流程和线下闸机：

```java
public VisitorAppointVerifyRespVO verifyVisitorAppoint(VisitorAppointVerifyReqVO reqVO) {
    // 到访验证：根据凭证号 ticket 查询预约记录
    VisitorAppointDO entity = visitorAppointMapper.selectByTicket(reqVO.getTicket());
    VisitorAppointVerifyRespVO respVO = new VisitorAppointVerifyRespVO();
    if (entity == null) {
        // 凭证不存在 → 验证失败
        respVO.setPass(false);
        respVO.setMsg("凭证无效");
        return respVO;
    }
    // 凭证有效 → 返回访客姓名、被访企业
    respVO.setPass(true);
    respVO.setVisitorName(entity.getVisitorName());
    respVO.setVisitCompany(entity.getVisitCompany());
    respVO.setMsg("验证通过，欢迎到访");
    return respVO;
}
```

这段实现很克制，但也正因为它简单，恰好适合作为"二开前原貌"的样本。我从三个角度评论它。

**角度一：为什么用凭证号而不是身份信息做核销？** 核销入参只有 ticket 一个凭证号。这个设计把"人"和"约"解耦了——闸机核销时不需要读身份证、不需要联网查人脸库，只要凭证号对得上就算核销通过，速度快、离线也能跑。凭证号在审核通过时生成，本身就是一次性的授权令牌。

**角度二：这个原实现有一个我必须修的洞。** 它只校验了凭证"存在"，没校验凭证"有效"。什么意思？把这张表的记录翻一遍就知道：一条状态还是"待审核"的记录，理论上不该有 ticket，但一条"已通过"的记录被取消之后（已取消），如果它的 ticket 没被作废，拿着这个凭证号去核销，原实现照样返回"验证通过，欢迎到访"。这是典型的**凭证生命周期没有跟随单据生命周期**的缺陷。我改的时候补了三重校验：状态必须是"已通过"、预约到访时间必须覆盖当前时刻（过期作废）、核销成功后记录到达时间防止重复核销。

**角度三：响应对象直接携带访客姓名与被访企业**，让闸机端在放行的同时把信息展示给值班员——"验证通过，欢迎到访"之外，值班员能看到访客要去找哪家企业，必要时可以再口头确认。这种小的体验细节，单看代码觉得平淡，放到值班室场景里才知道有用。

## 审核与驳回：两个方法的对称设计

`auditVisitorAppoint` 和 `rejectVisitorAppoint` 是一对对称方法：前者把状态迁到"已通过"并生成 ticket，后者迁到"已驳回"并写入驳回原因。表里对应的字段是 `checkUser`（审核人）、`checkResult`（审核结果）、`rejectReason`（驳回原因）。

我重点说驳回原因。园区业务的驳回不能只是一个状态——访客被驳回了，得知道为什么，否则他会反复提交、打电话到运营台。驳回原因字段让驳回变成一个可沟通的动作。我在二开时进一步把驳回原因做成了枚举加备注：常用理由（被访人不在、预约时间过早、企业已退租）点选，特殊情况补充说明。运营的驳回操作从打字变成了两次点击，驳回的响应速度直接决定了访客的体验。

还有 `checkUser` 审核人这个字段，和上一章人脸库的 `handleUser` 一脉相承：**凡是人做的决策，都要留下人的痕迹**。审核是责任行为——审核通过意味着园区允许一个外部人员进入，出了事要能回答"是谁审的、依据是什么"。

## 离园登记：生命周期要有终点

`leaveVisitorAppoint` 是状态机的收尾：访客离开时登记离园时间，状态进入"已离园"。这个动作看起来平淡，但它是园区安全管理的兜底——**在园访客名单**是一个园区每天要回答的安全问题："现在园区里有多少访客、分别是几点进来的、访问哪家企业？"

答案就藏在状态与时间字段的组合里：状态为"已通过"且 `arriveTime` 已落值、`leaveTime` 为空的记录，就是当前在园访客。如果访客离园不登记，这个名单会越积越假——人走了，名单上还有他。我在二开时加了一道保险：每天闭园时间之后跑一个任务，把当天 `arriveTime` 非空但 `leaveTime` 为空的记录打上标记并提醒值班员人工确认，避免"幽灵访客"滞留在名单里。

顺带一提，这套状态机还支持 `cancelVisitorAppoint` 主动取消。取消的入口做了角色区分：访客自己在预约单上取消，不需要理由；运营代取消则要填原因。同一个动作在不同角色手里有不同的义务，这是权限设计里"动词的粒度"问题，第 10 章讲多租户权限时还会回到这个话题。

再补一个容易被忽视的时序细节：**取消与核销的竞态**。想象一个场景——访客已经在闸机口出示凭证核销，与此同时运营在后台取消了这张预约单，两个动作几乎同时发生。如果取消逻辑不校验前置状态（已核销的不能取消），或者核销不校验单据是否已被取消，就会出现"人已经进园了，单子显示已取消"的矛盾现场。我的处理是给两个动作都加了状态前置校验，且核销在校验通过后立即落 arriveTime——这个时间戳是冲突仲裁的最后依据：核销时间早于取消时间的，以核销为准并给运营推一条提醒。分布式场景下的时序问题没有银弹，能做的是把"最终权威"指定清楚，让矛盾出现时有章可循。

预约单还有一个"隐形成员"值得点名：**被访人**。原模型的字段只有 visitCompany（被访企业），被访人信息要么填在企业备注里，要么靠运营电话确认——找人这件事完全靠前台的记忆力。二开时我把被访人升格为结构化字段（姓名加部门），审核通知直接推给被访人确认（企业微信或短信），被访人点确认，审核才算通过的第一步。这个改动让"审"的动作从园区单方裁决变成了"被访人意愿在前、园区审核在后"的两段式，驳回率显著下降——很多驳回本来就不是园区不同意，而是被访人根本不知情。

## 生产化补强：原模型没覆盖的四个真实问题

五状态主线讲完了，这一节讲我在二开时补的四个边角。它们在 demo 里全部隐形，上线后个个都会来敲门。

**一是随行人员。** 现实中的访客很少一个人来：商务拜访带助理，施工进场带一个队。原模型一行预约对应一个访客，随行的三五个人就要填三五张预约单，审核人要点三次通过——体验灾难。我的改法是给预约单加了主从结构：主单是发起人，随行人员挂子表（姓名、证件、关系），审核一次、核销按人（每人独立凭证）。表结构的改动很小，但把"一次到访"作为业务单元而不是"一个访客"，运营和访客的感受完全不同。

**二是黑名单。** 有过滋扰记录的人员、被投诉的推销员，不能让他换个姓名再约一次就进门。我加了一张访客黑名单表（证件号为主键），创建预约与凭证核销两个入口都要过黑名单检查——命中即拦截并提示运营。黑名单的写入入口做了权限收敛，只有安保主管能加，加的时候必须填依据（事件记录编号），防止这个工具被滥用成"私人门槛"。

**三是预约容量控制。** 园区对同一时段的访客接待能力是有上限的——前台核销通道就那么几个，电梯承载是刚性的。原模型没有容量概念，一次展会带来的两百人预约能把前台冲瘫。我加的是时段容量配置（每个到访时段的最大可审核通过数），审核通过时检查容量，满了引导改约。这个功能很小，却把"审核通过率"从一个运营结果变成了运营手段。

**四是企业代约。** 高频被访企业（比如园区里的政务服务中心）提出了"我方主动邀请"的模式：被访企业填访客信息发起邀请，访客只需确认。流程上复用同一张表和状态机，只是创建入口多一个"代约"来源字段，审核环节可以配置为企业自审加园区备案。同一个状态机支撑两种业务姿势，这是本章开头说"状态机设计质量决定运营顺畅度"的最好注脚。

这四个补强没有一个动到五状态主线——它们全部长在状态机的入口、出口和旁路上。好的状态机就像好的地基，加层不加柱。

最后交代一下这章的接口安全设计。访客预约是对外开放的功能（访客在小程序上自助提交），它的接口暴露面比内部管理接口大得多，安全设计要换一套思路：提交接口做频率限制（同一手机号一天最多 N 张预约单，防刷单灌库）、审核接口只对持有对应权限串的角色开放、核销接口要求设备侧签名（闸机网关带密钥签名，防止凭证号被外部猜中刷核销）。特别是核销——它是唯一能把访客放进园区的动作，我们把它当成一个小型的"写权限极高"接口来防护：限流、验签、审计三样全配。对外功能的安全水位，取决于它暴露给最陌生用户的那条接口。

## 统计看板：状态机最后的红利

Service 里还有一个 `getVisitorAppointChart` 方法，给运营看板提供访客数据统计。这里我想说状态机设计的最后一层红利：**当状态表达是干净的单字段互斥枚举时，统计就变成了 GROUP BY**。今日预约数、通过率、驳回 Top 原因、平均到访时长（leaveTime 减 arriveTime 的均值），每一条都是对状态和时间字段的一次聚合，不需要任何数据清洗。

访客这条线讲完了。回看这一章的方法清单：创建、审核、驳回、核销、取消、离园、统计，九个方法覆盖了五状态迁移的全部路径，每个方法守一段状态边。下一章进入停车业务，先讲车位台账与账单生成——那是园区里离钱最近的地方，数字必须分毫不差。
