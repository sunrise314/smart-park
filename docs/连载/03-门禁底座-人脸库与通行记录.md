# 门禁底座：人脸库与通行记录

园区平台的所有业务里，门禁是实时性最强、出错代价最直接的一块——闸机卡住三秒钟，门口就开始排队。这一章讲门禁业务的地基：人脸库管理（授权侧）和通行记录（执行侧）这两张表怎么设计，以及原项目围绕它们组织的业务逻辑。理解了这对"授权-执行"模型，你会发现访客、车辆、车位本质上都是它的变体。

## 人脸库：不只是"存一张脸"

很多人对门禁系统的想象停留在"设备认出人脸就开门"，但工程上真正难的是人脸背后的**权限管理**：这个人是谁、属于哪家企业、能通行的区域是哪里、权限什么时候到期。原项目把这部分沉淀在 `face_mgmt` 表里，对应 `FaceMgmtDO`，原文如下：

```java
@TableName("face_mgmt")
public class FaceMgmtDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * [人员姓名] 人员姓名
     */
    private String userName;
    /**
     * [手机号] 手机号
     */
    private String phone;
    /**
     * [所属企业] 所属企业
     */
    private String company;
    /**
     * [通行区域] 通行区域
     */
    private String accessArea;
    /**
     * [权限有效期] 权限有效期
     */
    private LocalDateTime authValidity;
    /**
     * [权限状态] 如:已授权/未授权/已过期
     */
    private String authStatus;
    /**
     * [通行次数] 通行次数
     */
    private Integer accessCount;
    /**
     * [最后通行时间] 最后通行时间
     */
    private LocalDateTime lastAccessTime;
    /**
     * [验证准确率] 验证准确率
     */
    private BigDecimal verifyAccuracy;
    /**
     * [操作人账号] 操作人账号，关联芋道用户表
     */
    private String handleUser;
}
```

这个表设计里有三个字段值得停下来分析。

**第一个是 `authValidity` 权限有效期**。园区的人员流动非常频繁：实习生到期离职、外包合同结束、访客授权只给一天。如果权限只有"开/关"两态，运营人员就得天天手工关权限，漏关一个就是安全隐患。有效期字段让权限自带 TTL——设备侧同步人脸时把有效期一并下发，闸机本地比对时间，过期自动拒绝。我在二开时给这个机制补了一条兜底：每天凌晨一个定时任务扫 `auth_status = '已授权' AND auth_validity < now()` 的记录，批量刷新成"已过期"。为什么有了设备侧判断还要刷库？因为运营看板上的"在授权人数"统计来自数据库，库里的状态不刷新，报表就是假的。

**第二个是 `verifyAccuracy` 验证准确率**。这个字段记录的是最近一次人脸比对的置信度，它暴露了一个容易被忽略的事实：人脸识别是概率问题，不是布尔问题。光照变化、戴口罩、发型改变都会让同一张脸的比对分数浮动。原项目把这个值落库，我顺着它做了两件事：一是给置信度设了分级阈值（高于阈值直接放行，介于中间时提示人工复核），二是用它来发现"该重新采集的人"——某个员工的近期准确率持续走低，大概率是他的注册照片太旧了，系统提醒运营重新录脸。

**第三个是 `handleUser` 操作人账号**，注释里明确写了"关联芋道用户表"。人脸库是运营人员手工维护的数据，每一次录入、修改、授权都要留下"是谁操作的"这个审计线索，出问题时才追得到人。这正是上一章讲的 BaseDO 审计机制之外，业务级的补充审计。

## 通行记录：一条流水里的完整闭环

授权侧管"谁能过"，执行侧管"过了什么"。通行记录落在 `access_record` 表，`AccessRecordDO` 原文：

```java
@TableName("access_record")
public class AccessRecordDO extends BaseDO {

    @TableId
    private Long id;
    /**
     * [人脸信息ID] 关联人脸信息表主键
     */
    private Long faceId;
    /**
     * [人员姓名] 通行人员姓名
     */
    private String userName;
    /**
     * [通行区域] 通行区域
     */
    private String accessArea;
    /**
     * [通行时间] 通行发生时间
     */
    private LocalDateTime accessTime;
    /**
     * [验证方式] 验证方式
     */
    private String verifyType;
    /**
     * [通行状态] 通行状态
     */
    private String accessStatus;
    /**
     * [抓拍照片] 通行抓拍照片存储路径
     */
    private String snapImg;
    /**
     * [核查结果] 异常通行核查结论
     */
    private String checkResult;
    /**
     * [告警状态] 异常通行告警内容
     */
    private String alarmStatus;
    /**
     * [处置结果] 异常通行处置结论
     */
    private String handleResult;
}
```

设计上我第一个想强调的是**冗余存储 userName 的决策**。通行记录已经有 `faceId` 可以关联到人脸表拿姓名，为什么还要存一份？因为通行记录是**流水**，人脸库是**档案**。流水必须自带快照语义：某人离职后，运营把他在人脸库的记录删了，但三个月前的通行流水必须还能独立读出"张三于某时通过某门"。如果流水只存外键，档案一删，流水就成了对不上的烂账。这种"流水带冗余、档案管现状"的分离原则，在访客表（存访客姓名）、停车账单（存车牌号）里反复出现，是园区数据模型的一条主线。

第二个想说的是**异常通行的三个字段**：`checkResult` 核查结果、`alarmStatus` 告警状态、`handleResult` 处置结果。这三个字段合起来描述了一个异常处置的完整工作流：设备识别出陌生人脸或尾随 → 记录进入告警态（alarmStatus 写入告警内容）→ 安保人员核查监控与抓拍照片（checkResult 写入核查结论）→ 形成处置动作（handleResult 写入"已劝离"、"已放行"等结论）。原项目把状态用三个独立字段而不是一个枚举来表达，好处是每个环节都可以独立查询——"今天有多少条未核查的告警"就是一条 `alarm_status 非空 AND check_result 为空` 的查询，不需要解析复合状态。

`snapImg` 存抓拍照片的**路径**而不是照片本身，这也遵循了通用的工程纪律：数据库存引用，对象存储存内容。抓拍照片每天几万张，塞进数据库既撑爆存储又拖垮备份，原项目把照片交给 infra 模块的文件服务，表里只留路径，查询详情时再按路径取图。

## 设备协议：门禁集成的真实复杂度

讲完表设计，必须聊聊绕不开的设备协议，这是门禁集成里最容易低估的部分。园区的人脸设备来源杂：主力品牌走各自的标准接口，长尾的 OEM 白牌设备走私有协议。原项目的做法是把协议适配收敛在采集上报这一层——设备侧或其配套的边缘网关完成识别比对，平台只接收标准化的通行事件，这层设计我很认同：**平台不碰比对算法，只管事件**。

但"只管事件"也有协议适配的活。不同设备上报的事件报文格式不一：字段名有的是驼峰有的是下划线，时间格式有秒级时间戳也有 ISO 字符串，抓拍照片有的给 URL 有的给 Base64。我的做法是在 accessmgmt 模块的 framework 层（框架约定的适配层位置）建了一个事件转换器接口，每个设备品牌一个实现：入口是原始报文，出口是统一的事件对象。新增设备品牌就是加一个转换器实现类，核心链路一行不改。

图片的处理要单独设计。Base64 直传的照片大、解析慢，统一在转换器里转成文件服务上传，事件里只留路径——这个决策和第 3 章讲的"snapImg 存路径"呼应，从协议入口就把内容挡在数据库外。

心跳与在线状态也归这层管。设备定期心跳，平台侧记录最近心跳时间，超时未心跳的设备标记离线——安防章讲的"设备健康度"在门禁域同样存在，闸机离线意味着这个出入口的人工登记通道要立刻启用，离线告警的价值就在这里。

## 通行报表：流水数据的三个出口

通行记录沉淀下来之后，数据有三个出口，对应三类使用者。

**第一个出口是实时大屏**。园区大厅的访客屏要展示"今日通行人次、当前在园人数、各出入口实时流量"。这些数字全部来自 access_record 的当日聚合，配上在园/离园的判定逻辑（进园事件与出园事件配对）。实时大屏的刷新频率控制在十秒级，聚合结果做短缓存，和后续章节的看板缓存策略一致。

**第二个出口是运营报表**。accessreport 包提供的是日周月的常规报表：各区域通行量趋势、高峰时段分布、异常通行占比。这类报表的查询模式固定，我做了预聚合表（按区域按小时汇总），报表查询只碰汇总表，几十万行的流水表只在钻取明细时才被打开。

**第三个出口是周期比对（cyclereport）**。原项目的 AccessCycleReportDO 做的是"周期通行报告"——比如某企业某月的到访人数、某楼栋的通勤规律。这类数据对招商部门是宝贝：给潜在租户展示园区的活跃度，比任何话术都有说服力。数据本身早就躺在流水表里，缺的只是按周期、按维度重新聚合的视角。

三个出口共享同一份流水数据，出口越多，越要守住"流水表只写不改、聚合外置"的纪律——一旦有人图方便直接在流水表上做业务更新，所有出口的数据可信度一起塌。

## 从设备到落库：通行链路的完整时序

把两张表串起来看一条通行的完整链路。以员工刷脸进门为例：

1. **设备侧识别**：闸机摄像头抓拍，本地或边缘服务器完成人脸比对，拿到 personId 和置信度；
2. **权限校验**：设备或平台侧校验该 personId 的授权状态与有效期，决定放行或拒绝；
3. **记录上报**：无论放行与否，设备把通行事件（时间、区域、验证方式、状态、抓拍照片）上报平台；
4. **落库分流**：平台收到事件，`AccessRecordService` 落一条通行记录；如果识别到的是已授权人员，顺带更新 `FaceMgmtDO` 的通行次数与最后通行时间；如果是异常事件，写入告警状态并推送给安防值班端；
5. **查询与统计**：运营端按区域、时间、人员、状态多维查询流水，报表模块按天聚合通行量。

注意第 3 步的表述——"无论放行与否都上报"。这是门禁数据的一条铁律：**拒绝通行的记录比成功通行的更有价值**。陌生人脸的反复尝试、已过期人员的到访、深夜时段的尾随，这些异常信号全部藏在"拒绝"的流水里。原项目的通行状态字段把成功与失败分开存，正是为了让这些信号可查。

链路里还有一个隐蔽但致命的环节值得单独叮嘱：**设备时间同步**。闸机侧的时间如果漂了几分钟，它上报的 access_time 就是错的——流水与考勤对不上、通行时间与监控录像对不上，所有以时间为轴的关联分析全部失真。我的做法是平台侧不信任设备时间：事件落库时记录两个时间——设备上报时间（access_time）与服务器接收时间（create_time 本身），校验逻辑发现两者偏差超过阈值（比如 60 秒）就打上"时间可疑"标记并告警，运维去现场校时。这个小小的双时间戳设计，后来在多次争议仲裁中起到了决定性作用——"到底是几点刷的门"，设备时间和接收时间的组合能把答案钉死。

多台设备的时钟漂移还有个系统性解法：支持 NTP 的设备统一配内网 NTP 服务器，不支持的设备纳入"时间可疑"监控清单重点盯防。设备侧的工程就是这样，一个大坑往往要靠几个小设计合围。

## 我在二开时动过的地方

原实现给了很好的骨架，但我落地时改了两处，这里如实交代。

第一处是**通行记录的写入批量化**。原实现的记录上报接口是单条插入，园区早高峰一个闸机每分钟几十条事件，多台闸机并发上报时，单条插入的数据库压力和网络往返都明显偏大。我把上报接口改成了批量语义：服务端用一个有界队列接收事件，消费端攒批（每 200 条或每 500 毫秒）批量插入。改动不大，但早高峰的入库延迟肉眼可见地平了。这里有个细节要小心：批量化之后，"通行次数 +1"的更新不能再和插入同步做（会跟批量写入竞争行锁），我把统计更新挪到了消费批次里统一处理。

第二处是**给 access_time 建了组合索引**。原表只有主键索引，运营端"查某个区域某天的流水"是全表扫描，园区跑了一个月之后这张表到几十万行，查询已经能感觉到慢。我建了 `(access_area, access_time)` 组合索引，报表类的范围查询直接走索引。流水表只增不改，索引的写入代价完全可接受。

门禁这一章是"授权-执行"模型的主线故事。下一章讲的访客预约，本质上是把这套模型扩展出一条**带审核流的旁路**——外部人员不能直接进人脸库，要先预约、再审核、审核通过才生成临时通行凭证。这个状态机比门禁本身精彩得多。
